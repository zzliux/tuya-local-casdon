# 模式枚举（DP105）采集进度

设备把「模式」编码成 DP105 的字符串数字。这台机器上目前只确认了少量取值，**其余仍是数字**。

> **`18` 和 `20` 未被使用**：App 的 21 个模式全部对上后，`1`–`17`、`19`、`21`–`23` 已占满，
> 只剩 `18`、`20` 两个空号，推测是保留位或未在当前固件启用（例如需要探针/水箱模块的功能）。

> **实测结论（2026-11-16）**：`105` 直接就是**叶子模式编号**，不是「大类」。
> 烧烤 10 个子模式分别是 `3`–`12`，无需 `106` 区分；此前「烧烤共用 105=3、靠 106 分流」的假设是错的。
> `106`（观测恒为 1）与 `109`（`no_preheat`）更像独立设置项，与模式无关。

> **采集方式差异**：杀菌 / 烘干 / 除垢**不支持预约**，只能直接启动后取消，因此没有 `reservation` 锚点，
> 只能靠操作时间对齐。其中「烘干」可暂停，「除垢」不可暂停。

## 为什么难

App 里的模式清单（用户提供）：

```
鲜蒸：纯蒸、高温蒸
烧烤：上下烤、3D热风、顶部热风、风扇烤、底部热风、大面积烤、下烤、低湿嫩烤、中湿嫩烤、高湿嫩烤
香炸：空气炸
炖：养生炖
速热：速热
更多：解冻、发酵、保温、杀菌（不可调）、烘干（不可调）、除垢（不可调）
```

**烧烤 11 个模式的默认值全是 180℃/20 分钟**，光靠「温度 + 时长」无法区分。真正区分它们的很可能是：

- `DP106`（观测到恒为 `1`，疑似「风扇/加热方式」）
- 或某个还没观测到的 DP

也就是说这是一个**两级结构**：`105` 选大类，`106` 选具体手法。目前只标定了 105，106 的枚举还没采到。

## 怎么补（推荐方法）

### 方法 A：预约法（已实测，最稳）

对每个模式重复一遍「设预约 → 记录 → 取消」：

1. 选目标模式，设一个**几分钟后结束的预约**（比如现在 21:10，就设 21:15 结束）
2. 等 HA 里状态变成 `reservation`
3. 取消预约
4. 换下一个模式

为什么稳：**预约时间是天然的时间锚点**。每次操作都会在历史里留下一条带明确时间戳的 `reservation` 记录，即使中途点错、多点了、顺序乱了，也能靠时间对回去。

一次操作会同时确定四个值：

| 字段 | 含义 |
| --- | --- |
| `105` / `program` | 模式 |
| `7` / `climate.temperature` | 该模式的默认温度 |
| `10` / `烹饪时间` | 默认时长 |
| `9` / `Start time` | **预约结束时刻**（不是开始时刻） |

实测样例（本地时间）：

| 时间 | 状态 | program | 温度 | 预约结束 |
| --- | --- | --- | --- | --- |
| 22:03:00 | reservation | `1` | 100℃ | 22:30 |
| 22:03:02 | wait（取消） | – | 0 | – |
| 22:03:10 | reservation | `2` | 110℃ | 22:35 |
| 22:03:12 | wait（取消） | – | 0 | – |

由此确认 `1 = 纯蒸`、`2 = 高温蒸`。

注意：**取消后 `Start time` 不会被清空**，会保留最后一次的值（上例里到现在还显示 22:35）。所以判断有没有预约要看 `状态 == reservation`，不要看这个实体。

### 方法 B：顺序点击法（没有预约功能时用）

按 App 里模式清单的**固定顺序**，每个点一下、停 3~5 秒，靠 DP 变化序列与清单顺序对齐。

避坑：

- 不要中途退出或点错重来，否则序列错位
- 杀菌/烘干/除垢可能压根不上报 DP，按缺失自动跳过
- 记录前先把设备恢复空闲（105 = `none`）

## 拿到映射后怎么用

仓库里已经提供两个方向：

- `select.*烹饪模式*`：可写，22 个选项（21 模式 + 「无」）
- `sensor.*烹饪模式（名称）*`：只读，输出同样的中文名，方便仪表盘/自动化引用

另有 `sensor.*烹饪模式（原始值）*` 保留设备原始数字，用于排错。

> 注意：写入 `select` 只改 DP105，**不会**同时设置温度/时长，启动前仍需单独设置。
